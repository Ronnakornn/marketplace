# Buyer and shop chat

Chat connects one buyer with an active shop owner. A buyer can also own other shops. Staff and administrators are outside this chat contract. Existing history remains readable when a shop disables chat, while room creation and new sends require an active shop with chat enabled. The platform chat feature guard still applies.

`GET /api/chats` accepts `scope` and an optional `shopId`. `GET /api/chats/:roomId` accepts `limit` up to 50 and one of `before` or `after`. Each cursor is a message UUID resolved inside the authorized thread. Messages are ordered by `(createdAt,id)` and returned chronologically. `pagination.hasMore` describes the requested direction; `beforeCursor` and `afterCursor` identify the oldest and newest returned messages. Legacy `page` pagination remains available, but new clients use cursors.

New text sends use a client-generated UUID as `clientMessageId`. The UUID identifies one immutable send including sender, room, normalized body, product and order context. Identical retries return `sentMessage` without duplicate publication or notification. Conflicting reuse returns 409 without exposing the original message. Messages allow at most 4000 characters after trimming. Product context must belong to the room shop; order context must belong to the room buyer and contain that shop. Context is stored on each message. Creating a room sends no message.

Sends and reads lock the thread row in a transaction. Each new message timestamp exceeds the greatest existing timestamp by at least one millisecond, including legacy messages with missing `lastMessageAt`. Read acknowledgements supply `throughMessageId` in the query string and advance the participant's `(readAt,readMessageId)` boundary monotonically. Reading never updates activity order. A legacy request without an ID acknowledges the latest committed message; it cannot guarantee that the message was rendered by that client. Existing timestamp-only boundaries preserve their old semantics until a newer explicit acknowledgement.

Realtime publishes room changes to `chat:<roomId>`, `seller:<shopId>:chats` and `user:<buyerId>:chats`. Each delivery revalidates session and participant access. The client treats realtime as a recovery signal, fetches ascending `after` pages from its contiguous cursor, and deduplicates by ID. A sent response can appear immediately but cannot advance that cursor before catch-up fills potential gaps. Only focused, visible bottom-of-thread viewing acknowledges the latest contiguous rendered message. Visible fallback polling and reconnect recovery cover missed events.

New image messages are rejected until participant-authorized attachment storage exists. Legacy images render as placeholders, and their external URLs are never fetched.

Run the PostgreSQL contract suite with `CHAT_TEST_DATABASE_URL` pointing to an isolated local database whose name ends in `_test`. Apply migrations and generate Prisma before running `bun run test server/modules/chat server/modules/realtime`. The chat migration is additive and introduces two nullable read-message IDs and the composite message-order index.

The inbox supports search and unread filtering. Seller navigation uses the selected owned shop consistently. Failed sends preserve the draft and reuse the original message ID for retries; a completed request cannot clear a newer draft. Cached sessions and queries hydrate consistently. On mobile, the conversation scrolls inside the available viewport and keeps the composer above the bottom navigation.

Known chat errors preserve their HTTP status and error code through the observability middleware. Unexpected errors retain the application's redacted response. Clients can therefore explain disabled chat and participant-access errors without exposing internal failures.
